# 我的账本工具 · 产品规格

> 状态：草案（待调研结论回填类目体系）
> 生成方式：`to-spec` 综合本次会话共识，不做二次访谈
> 文档规则：文档文件名用中文，代码/目录/配置用英文

## 问题陈述

我每个月都能从微信和支付宝导出账单，但拿到手的是两个格式各异的文件：微信是单 Sheet 的 `.xlsx`，支付宝是 GB18030 编码的 `.csv`，字段名不同、日期格式不同、还有大量不构成真实支出的记录。

以个人导出样本为例：微信与支付宝各一份账单，其中微信约 1/10 的记录是**中性交易**。如果不识别中性交易，本月支出会被算成两倍以上——这类错误不是精度问题，是结论方向错误。

现有工具都不合手：

- 开源自托管工具（Firefly III、Actual Budget 等）主要面向欧美银行 CSV，不认微信/支付宝的导出格式与中文商户名；
- 国内商业记账 App 以手动录入为核心，账单导入是附属功能，且数据默认上云；
- 纯文本记账（beancount）能力强，但需要我先把手写规则配好，学习成本落在最不想花时间的地方。

我需要的是：**把导出的账单文件变成可信的月度结论**，数据一步都不离开本机。

## 解决方案

一个只在本机运行的单进程 Web 应用：拖入账单文件 → 解析归一化 → 幂等入库 → 标记中性交易 → 规则优先分类 → 未命中项进待确认队列（人工确认后沉淀为规则）→ 看板与明细。

三条硬边界：

1. **只绑 `127.0.0.1`**，无账号体系，无公网入口；
2. **数据只落本机 SQLite**，不发任何外部网络请求；
3. **不做日常记账**，也不做对话式问账——查账是固定看板加明细筛选。

## 用户故事

### 导入

1. 作为用户，我把微信导出的 `.xlsx` 拖进页面，希望直接读出全部交易，而不需要我先手工转格式。
2. 作为用户，我把支付宝导出的 `.csv` 拖进页面，希望编码被自动识别（GB18030 / UTF-8），不出现乱码。
3. 作为用户，我重复导入同一个文件时，希望不产生任何重复记录。
4. 作为用户，我导入跨月重叠的两次导出时，希望重叠部分只保留一份。
5. 作为用户，我导入时能看到进度：已解析笔数、已分类笔数、剩余笔数。
6. 作为用户，导入结束后我能看到本次新增、跳过、失败各多少笔。
7. 作为用户，某几行解析失败时，我能看到行号与失败原因，而不是整批失败。
8. 作为用户，文件既不像微信也不像支付宝时，我希望能明确报错，而不是被猜成其中一种。
9. 作为用户，我希望文件里出现未知列时给出警告但仍导入能识别的部分。

### 分类

10. 作为用户，常见商户（美团、滴滴、京东、星巴克、中石化等）按内置规则直接分类。
11. 作为用户，规则未命中的交易进入待确认队列，由我确认或改选类目。
12. 作为用户，确认时可以勾选「学习关键词规则」，下次相同商户自动分类。

> 以下为**规划中、当前未启用**的可选增强：规则未命中的交易由本地模型给出
> 二级类目与置信度，置信度低于阈值时仍标记为「待确认」。代码入口见
> `app/classify.py` 与 `myledger classify-pending`，需要自行部署 `llama-server`。
13. 作为用户，我可以修改任意一笔的类目，修改后同类商户的后续交易自动沿用这个类目。
14. 作为用户，我可以新增、重命名、停用二级类目，且这些操作不改变历史数据的归类结果。
15. 作为用户，我可以一次性导入一套类目体系，而不是从空白开始建。
16. 作为用户，我改完规则后可以批量重跑分类，并看到有多少笔结果发生变化。
17. 作为用户，我能看到每笔分类的来源：规则命中 / 人工修改（启用模型后另含模型判定）。

### 中性交易

18. 作为用户，提现、充值、理财通购买、零钱通存取、信用卡还款被标记为中性交易，不计入收入也不计入支出。
19. 作为用户，我在看板上能单独看到中性交易总额，避免把钱「消失」误读为消费。
20. 作为用户，我可以把某一笔中性交易手动改回支出或收入。

### 看板

21. 作为用户，我在月度总览里看到收入、支出、净额与交易笔数。
22. 作为用户，我能看到分类占比，并可在一级/二级类目之间切换。
23. 作为用户，我能看到最近 6 个月的趋势。
24. 作为用户，我能看到 Top 商户与 Top 单笔金额。
25. 作为用户，我能按数据源（微信 / 支付宝）分别查看以上所有指标。
26. 作为用户，我点击图表中的某个类目时能下钻到对应的明细列表。

### 明细

27. 作为用户，我能按时间区间、金额区间、类目、数据源、关键字筛选明细。
28. 作为用户，我能对明细排序与分页。
29. 作为用户，我能同时看到原始摘要与归一化后的商户名，以判断分类是否合理。
30. 作为用户，我能把当前筛选结果导出为 CSV。

### 隐私与数据控制

31. 作为用户，我能确认应用没有任何外部出站请求（启用可选本地模型时也只请求 `127.0.0.1`）。
32. 作为用户，我知道真实账单不会进入代码仓库。
33. 作为用户，我能一键清空全部本地数据。

### 运维

35. 作为用户，我用一条命令启动应用。
36. 作为用户，首次运行时数据库与表结构自动创建，升级时自动迁移。
37. 作为用户，我能看到当前数据的覆盖时间范围，以判断是否需要补导入。

## 实现决策

**模块划分**

- 解析器（按数据源各一个）：负责文件解码、表头识别、行映射、错误定位。只输出「原始行 → 未归一化交易」。
- 归一化：统一时间为本地时间、金额为「分为单位的整数」、方向为「收入/支出/中性」。
- 存储：SQLite，schema 带单调递增版本号，迁移按版本顺序执行。
- 分类：规则引擎（商户关键词 / 正则 / 历史人工结论）优先；未命中项进待确认队列，人工确认后沉淀为规则。
- 聚合与查询：全部在 SQL 完成，前端不做计算。
- HTTP 层：标准库 `ThreadingHTTPServer`；导入在请求内同步完成。
- 前端：无构建步骤的原生 HTML/CSS/JS，聚合在浏览器端按区间计算。

**关键约定**

- 幂等键：`(数据源, 交易单号, 商户单号, 交易时间, 金额分)` 上的唯一约束；缺单号时退化为 `(数据源, 交易时间, 金额分, 摘要哈希)`，并在导入报告中标注「弱去重」。
- 金额一律存整数分，杜绝浮点误差。
- 中性判定由数据源字段映射白名单决定，不由摘要文本猜测。
- （可选、未启用）模型输出受 JSON schema 约束：只允许枚举内的类目与 `0..1` 置信度；解析失败按「待确认」处理。
- 若启用模型：调用不阻塞导入，导入先落库并标记 `pending`，分类是独立可重入的批处理。
- 分类来源字段与置信度字段必须可查询，看板能按「待确认」筛选。
- 鉴权：scrypt 密码哈希 + HttpOnly 会话 cookie；多用户按 `owner_id` 隔离。
- 默认只监听 `127.0.0.1`；公网部署需自备 TLS 反代。不引入远程字体、CDN 或统计脚本。

**数据源字段假设**（以本机两份真实导出为准，实现前需再次核对）

- 微信：`交易时间`、`交易类型`、`交易对方`、`商品`、`收/支`、`金额(元)`、`支付方式`、`当前状态`、`交易单号`、`商户单号`、`备注`。
- 支付宝：`交易时间`、`交易分类`、`交易对方`、`商品说明`、`收/支`、`金额`、`收/付款方式`、`交易状态`、`交易订单号`、`商家订单号`、`备注`。

**类目体系**

v1 的两级类目来自调研结论，不在本规格内定稿。规格只约束：一级类目数量不超过 12，二级类目可增删改停，历史归类不随类目改名漂移。

## 测试决策

**好测试的判据**：只断言外部可观测行为——给定账单文件，得到什么入库结果；给定数据库，聚合出什么数字。不断言内部函数调用次数、不断言 SQL 文本、不为覆盖率写测试。

**测试边界**（靠参数化、依赖注入、模块化实现；凡是“不启动真模型、不读死路径就没法测”的设计都要改）：

- 主边界 —— HTTP 接口层：应用由 `createApp({ 数据库路径, 模型客户端 })` 装配，测试传入临时 SQLite 与假模型，走「导入 → 查询 → 聚合」的真实路径。
- 次边界 —— 解析器：独立纯函数模块（字节 → 交易数组），无 IO、无全局状态，可单独调用。
- 冒烟 —— 前端一条：页面能加载并显示总笔数。

- 解析器单测：微信 xlsx 与支付宝 GB18030 csv 两份脱敏 fixture，覆盖正常行、空行、中性行、缺单号行。
- 幂等：同一文件导入两次，交易表行数与聚合结果均不变。
- 中性：fixture 含提现与信用卡还款，断言其不进入支出合计。
- 模型兜底：假模型返回固定类目，断言写库的类目、来源、置信度三项。
- 聚合：对固定数据集断言月度收入/支出/净额与分类占比的分母口径。
- 前端：一条冒烟——页面能加载并显示总笔数。

## 范围外

- 日常手动记账、自然语言记账、语音记账。
- 对话式问账（自然语言查询与回答生成）。
- 银行流水、信用卡账单、券商与基金对账单导入。
- 多币种与汇率。
- 退款冲销（v1 记为已知偏差，退款按原方向计入）。
- 跨平台资金流配对（微信 ↔ 支付宝 ↔ 银行卡互转识别）。
- 预算、提醒、账单到期日。
- 局域网访问、手机端、公网部署、多用户与鉴权。
- 云同步与自动备份。
- 与任意第三方服务的数据交换。

## 补充说明

- **已知偏差登记**：退款不做冲销；跨平台资金流不做配对。两项都会在看板的脚注中展示，避免用户误读。
- **模型选型**：MiniCPM-V 4.7 1B，经 `llama.cpp` 的 `llama-server` 暴露 OpenAI 兼容接口。本机为 16 GB 内存、MX250 2 GB 显存，35B-A3B 档不可用。
- **规则优先的原因**：小模型在中文商户名上的分类准确率不足以独自承担结论；规则优先让错误集中在规则未覆盖处，可被人工快速修正并沉淀为规则。
- **本规格的类目章节等调研报告回填后再定稿。**
- **文档规则**：文档文件名使用中文；目录、代码、配置、脚本使用英文；根目录的 `README.md`、`AGENTS.md`、`INDEX.md`、`CHANGELOG.md` 保留英文名。
